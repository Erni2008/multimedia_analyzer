========================================================================
1. REQUIREMENTS ANALYSIS
========================================================================

1.1 Product Vision

MultimediaAnalyzer is a web-based application for authenticated users who need
to analyze spoken content from audio and video. The platform supports media
upload, asynchronous processing, transcript generation, summarization, named
entity extraction, and detection of user-defined watchlist matches. Analysis
results are stored in a persistent database and displayed in a responsive UI.

1.2 Actors

- Authenticated User
- Administrator / Evaluator
- Background Worker
- External AI services or local AI runtime (integration-ready)

1.3 User Stories

US-01: As a user, I want to register so I can access my private workspace.
US-02: As a user, I want to sign in securely so I can manage my data.
US-03: As a user, I want to upload audio or video so the system can analyze it.
US-04: As a user, I want the upload to process in the background so the UI
       remains responsive.
US-05: As a user, I want a transcript of spoken content.
US-06: As a user, I want a concise summary of the transcript.
US-07: As a user, I want named entities extracted from the content.
US-08: As a user, I want to define a watchlist of important entities.
US-09: As a user, I want alerts when watched entities are detected.
US-10: As a user, I want to see historical results in one dashboard.
US-11: As an evaluator, I want a documented prototype and test artifacts.
US-12: As an administrator, I want containerized deployment for repeatability.

1.4 Main Use Cases

UC-01 Register user
UC-02 Login user
UC-03 Upload media file
UC-04 Queue media analysis
UC-05 Transcribe media
UC-06 Summarize transcript
UC-07 Extract named entities
UC-08 Compare entities with watchlist
UC-09 Save analysis results
UC-10 View dashboard results
UC-11 Update watchlist
UC-12 Review alert matches

1.5 Functional Requirements

FR-01 The system shall support user registration and login.
FR-02 The system shall issue JWT tokens for authenticated access.
FR-03 The system shall allow authenticated users to upload media files.
FR-04 The system shall persist media metadata and outputs in PostgreSQL.
FR-05 The system shall process uploads asynchronously using Celery and Redis.
FR-06 The system shall support audio extraction from video files via FFmpeg.
FR-07 The system shall generate a transcript for each uploaded file.
FR-08 The system shall generate a summary for each transcript.
FR-09 The system shall extract named entities from the transcript.
FR-10 The system shall allow users to maintain a watchlist of entities.
FR-11 The system shall flag and store alert matches.
FR-12 The system shall display results in a browser dashboard.

1.6 Non-Functional Requirements

NFR-01 The system shall be containerized with Docker and Docker Compose.
NFR-02 The UI shall be responsive for desktop and mobile.
NFR-03 The system shall isolate user data by authenticated session.
NFR-04 The solution shall separate API, worker, database, and frontend roles.
NFR-05 The project shall include test design and specification artifacts.

5. STATE DIAGRAMS
========================================================================

Two main state models are defined.

5.1 MediaAsset Lifecycle

queued -> processing -> completed
queued -> processing -> alerted
queued -> processing -> failed

Interpretation:

- A new uploaded file enters the queued state.
- The worker moves it to processing.
- If analysis finishes without watchlist matches, the result is completed.
- If watchlist matches exist, the result is alerted.
- If extraction or processing fails, the result is failed.

5.2 User Session Lifecycle

anonymous -> registered -> authenticated -> anonymous

Interpretation:

- A visitor starts anonymous.
- After account creation, the visitor becomes registered.
- After login, the visitor is authenticated.
- On logout, the user returns to anonymous state.

Source file:
docs/assignment/state_diagrams.mmd

6. SEQUENCE DIAGRAM AND ACTIVITY DIAGRAMS
========================================================================

6.1 Sequence Diagram: Main Application Flow

Main sequence:

1. User logs in on the frontend.
2. Frontend calls the FastAPI login endpoint.
3. API validates the user against PostgreSQL and returns a JWT.
4. User uploads a media file.
5. Frontend posts the file to the API.
6. API stores media metadata and queues a Celery task.
7. Celery/Redis dispatches the task to the worker.
8. Worker processes the file and writes results to PostgreSQL.
9. User refreshes the dashboard.
10. Frontend fetches stored results from the API.

Source file:
docs/assignment/sequence_main_process.mmd

6.2 Activity Diagram: Upload and Analysis

This activity diagram models the full ingestion and processing pipeline:

8. TESTING STRATEGY AND TEST CASES
========================================================================

8.1 Strategy

The testing approach is based on use-case traceability.

Test layers:

- Unit tests for auth and media helper functions
- API tests for login, upload, and watchlist endpoints
- Integration tests for database persistence and background processing
- UI validation for the main user flow
- Acceptance testing against the assignment use cases

8.2 Core Test Cases

TC-01 Register New User
- Preconditions: email not present in database
- Steps: enter credentials, click Register
- Expected: account created, token issued, session active

TC-02 Login Existing User
- Preconditions: user exists
- Steps: enter valid credentials, click Sign In
- Expected: token returned, dashboard loads

TC-03 Upload Audio File
- Preconditions: authenticated session
- Steps: select audio file, queue processing
- Expected: file stored, media record created, processing starts

TC-04 Upload Video File
- Preconditions: authenticated session
- Steps: select video file, queue processing
- Expected: audio extraction path triggered, status progresses

TC-05 Update Watchlist
- Preconditions: authenticated session
- Steps: edit watchlist, save
- Expected: values stored and reloaded

TC-06 Alert Match Detected
- Preconditions: watchlist contains a detected entity
- Steps: upload file, wait, refresh dashboard
- Expected: status = alerted, alert_matches populated

TC-07 Unauthorized Upload Attempt
- Preconditions: no active session
- Steps: attempt upload
- Expected: blocked in UI or rejected by API

TC-08 Invalid Login
- Preconditions: wrong password
- Steps: sign in with invalid credentials
- Expected: access denied, error displayed
