1. EXECUTIVE SUMMARY
========================================================================

MultimediaAnalyzer is a full-stack application concept and working MVP
prototype designed for the analysis of spoken content in audio and video
materials. The system allows authenticated users to upload multimedia files,
process them asynchronously, generate transcripts and summaries, detect named
entities, compare these entities against a user-defined watchlist, and store the
results for later inspection.

The objective of this submission is twofold:

1. Provide a complete software engineering specification package covering
   analysis, modeling, prioritization, testing, and UI design.
2. Demonstrate that the implemented prototype follows the designed
   specification and can be extended into a production-grade application.

The current implementation already contains:

- FastAPI backend
- JWT authentication
- SQLAlchemy persistence
- PostgreSQL-ready schema
- Celery worker pipeline
- Redis broker integration
- FFmpeg-ready media handling
- React/Next.js dashboard
- Watchlist and alert logic

This document consolidates the required academic deliverables into a single
submission-ready file.

2. REQUIREMENTS ANALYSIS
========================================================================

2.1 Product Objective

The system must help users analyze recorded speech content from uploaded media.
It is intended for review of interviews, meetings, podcasts, news clips,
training sessions, or other audio/video records where rapid content extraction
and entity-based alerting are valuable.

2.2 Problem Statement

Manual review of long audio and video recordings is slow and inefficient. Users
need a system that can:

- ingest media files,
- convert speech into text,
- summarize the content,
- extract important named entities,
- and signal when specific monitored entities are mentioned.

2.3 Stakeholders

- End users performing content review
- Instructors / evaluators reviewing the assignment
- Developers extending the system
- Administrators deploying the environment

2.4 Actors

- Authenticated User
- Administrator
- Background Worker
- Optional AI provider or local AI runtime

2.5 User Stories

US-01 As a user, I want to register so I can access a protected workspace.
US-02 As a user, I want to log in securely so I can access only my own records.
US-03 As a user, I want to upload audio or video files for analysis.
US-04 As a user, I want processing to run asynchronously so the UI stays usable.
US-05 As a user, I want a transcript from uploaded media.
US-06 As a user, I want a summary so I can review the content quickly.
US-07 As a user, I want named entities extracted from the transcript.
US-08 As a user, I want to manage a watchlist of important entities.
US-09 As a user, I want to be alerted when a watched entity appears.
US-10 As a user, I want to view past results in one dashboard.
US-11 As an evaluator, I want all software engineering artifacts clearly
      documented in one deliverable.
US-12 As an administrator, I want the app stack to run in containers.

2.6 Use Cases

UC-01 Register user

UC-06 Summarize transcript

2.7 Functional Requirements

FR-01 The system shall support account registration.
FR-02 The system shall support account login.
FR-03 The system shall use JWT for session authentication.
FR-04 The system shall allow authenticated users to upload media.
FR-05 The system shall persist uploaded file metadata.
FR-06 The system shall queue processing through a worker.
FR-07 The system shall support audio extraction from video.
FR-08 The system shall generate transcript output.
FR-09 The system shall generate summary output.
FR-10 The system shall generate named entity output.

NFR-05 The solution shall be demonstrable as a functional MVP.

3. REQUIREMENTS PRIORITIZATION (MoSCoW)
========================================================================

The selected prioritization method is MoSCoW:

- Must: essential for the MVP and assignment objective
- Should: strongly valuable and expected in a polished version
- Could: beneficial extensions if time permits
- Won't: intentionally excluded from current scope

Priority decisions:

- Authentication, upload, processing, persistence, and dashboard visibility are
  mandatory because they define the core business value.
- Summarization, NER, watchlist configuration, and alert presentation are
  highly important and should be part of the intended system behavior.
- External notifications and advanced filtering are enhancements rather than
  MVP blockers.
- Anonymous access is intentionally excluded because it conflicts with secure
  user-specific result storage.

Detailed prioritized table is included in Appendix A and exported in:
docs/assignment/prioritized_requirements.csv

6. STATE DIAGRAMS
========================================================================

6.1 MediaAsset State Model

The MediaAsset entity is state-driven because processing is asynchronous.

States:
- queued
- processing
- completed
- alerted
- failed

State logic:

- queued is assigned immediately after upload.
- processing is assigned when the worker starts.
- completed is assigned when processing ends without watchlist matches.
- alerted is assigned when watchlist matches exist.
- failed is assigned when the pipeline encounters a processing error.

6.2 User Session State Model

The user interaction lifecycle has its own compact state model:

- anonymous
- registered
- authenticated

The logout operation transitions authenticated users back to anonymous state.

State diagram sources are embedded in Appendix B.

7. SEQUENCE AND ACTIVITY DIAGRAMS
========================================================================

7.1 Sequence Diagram: Main Process

The primary sequence demonstrates full system collaboration:

1. User logs in through the frontend.
2. Frontend calls the FastAPI authentication endpoint.
3. API validates the user in PostgreSQL.
4. API returns JWT token.
5. User uploads media through the dashboard.
6. API stores media metadata and queues a Celery task.
7. Redis passes the job to the worker.
8. Worker processes the media.
9. Worker saves outputs back to PostgreSQL.
10. User refreshes the dashboard to review results.

This sequence shows correct separation of synchronous and asynchronous work.

7.2 Activity Diagram: Upload and Analysis

This activity diagram models the complete media ingestion process from file
selection to stored results.

7.3 Activity Diagram: Watchlist and Alerting

This activity diagram models the capture of watchlist settings and the later
comparison of detected entities during analysis.
